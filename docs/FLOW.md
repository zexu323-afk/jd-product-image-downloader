# 主图与详情图下载流程

## 1. 为什么分成两层

浏览器负责“发现哪些文件属于当前商品”；下载器负责“把明确的链接安全地保存为文件”。两层只传递分类、链接和商品页 Referer，不向下载器传递 Cookie、登录密码或浏览器配置。

## 2. 主图来源与顺序

`_material_tasks()` 先检查 `.image-carousel-track .item img.image`；无结果再检查旧版商品缩略图容器；仍无结果才使用 `pageConfig.product.imageList`。仅检查商品所属区域，不收集整页广告和推荐商品图。

读取 `src` 和常见懒加载属性；协议相对链接补 `https:`，主图中 `/jfs/` 路径沿用原有 800×800 CDN 规范化策略。主图保留发现顺序与重复项，不擅自按文件去重，避免改变轮播位置语义。它仍不保证完整处理所有未来懒加载模板。

## 3. 详情图来源

`_detail_image_urls()` 在当前商品页面等待已存在的 `PSign.sign`，使用页面自身的签名和临时参数请求 `pc_description_channel` 详情内容。没有离线破解签名、复制账号会话或自动处理验证码。

对返回内容解码，提取 HTTPS 图片链接，只保留 `.360buyimg.com` 子域且路径含 `/jfs/` 的候选。按移除查询参数后的链接去重，保留首次出现顺序。不能取得详情来源时明确失败，不把空集合当作“没有详情图”。页面脚本或接口变化可能令这条路线失效。

## 4. 下载与校验

1. 命令版本为 1，每批最多 200 个文件。
2. 只允许受控的 HTTPS 媒体域名和 443 端口；重定向目标也重新校验。
3. 不继承系统代理或浏览器 Cookie，使用必要 Referer。
4. HTTP 401/403/429、HTML 验证响应形成明确阻断错误。
5. 检查 Content-Type、文件头、字节上限、空文件、Content-Length；流式计算 SHA-256。
6. 全部任务完成后生成分类 ZIP，并计算 ZIP 的 SHA-256。
7. 独立入口最后写入 `manifest.json`，作为本次完成标记。

单文件上限沿用原下载器的 512 MiB，网络操作有超时；本示例没有队列级进程隔离、总运行时长限制和磁盘额度系统。

## 5. 与原系统的关系

原系统还会把下载结果交给业务层，进行路径/哈希复核、证据入库、历史集合比较及前端展示。本仓库到“文件、ZIP、成功清单”结束，不复制这些业务依赖。若以后增加图片变化比较，文件哈希只能识别内容是否相同，不能解释画面改变了什么。
